# Carina Memory and RAG System

## Overview

Carina has three distinct but complementary memory systems:

1. **Conversational memory:** Per-session message history stored and retrieved from the active backend
2. **Persistent memory:** Long-term facts, preferences, and learned information that persists across sessions
3. **RAG (Retrieval-Augmented Generation):** Chunked knowledge documents embedded in pgvector,
   retrieved by semantic similarity at query time

All three are backed by the same abstraction layer in `src/memory/` and are queried transparently
by the agent without the user needing to specify which system to use.

## Memory Backends

Five backends are available, selected via `CARINA_MEMORY_BACKEND` environment variable:

| Backend | Driver | Best For |
|---|---|---|
| `builtin` | SQLite (bundled) | Development, self-hosted single-user |
| `postgres` | PostgreSQL + pgvector | Production multi-tenant, full RAG support |
| `sqlite` | SQLite (external) | Lightweight self-hosted |
| `mem0` | Mem0 cloud API | Managed memory service |
| `honcho` | Honcho cloud API | Managed memory with user modeling |

The backend interface is defined in `src/memory/backends/types.ts`. All backends implement:
- `saveMemory(sessionId, role, content)` - store a message
- `searchMemory(query, limit)` - semantic search
- `getSessionHistory(sessionId, limit)` - retrieve conversation turns
- `clearSession(sessionId)` - delete a session's history
- `listRecentMemories(limit)` - list recent entries

## Persistent Memory

The `memory` tool (`src/tools/memory.ts`) gives the agent direct read/write access to its
long-term memory store. This is separate from conversation history. The agent uses it to:
- Remember user preferences ("user prefers bullet lists over paragraphs")
- Store facts that are frequently referenced ("user's primary email is...")
- Track commitments ("follow up with X on Friday")
- Build a growing model of the user across sessions

Persistent memory is scoped per workspace in multi-tenant deployments. One tenant's memories are
never visible to another.

## REM (Random-access Episodic Memory)

REM is the self-improvement memory system. Files under `src/memory/rem/`:

- `rem-scorer.ts`: Scores existing memory entries by quality and relevance
- `rem-promotion.ts`: Promotes high-value episodic memories to the curated long-term store
- `rem-scheduler.ts`: Runs REM maintenance on a background schedule
- `dreams.ts`: Manages `DREAMS.md` - a queue of promoted memories awaiting curation

The flow: session memories accumulate in the episodic store. The REM scheduler runs periodically,
scores each memory entry, and promotes the highest-value entries to the `DREAMS.md` promotion
queue. The agent reviews the promotion queue and incorporates valuable memories into its long-term
knowledge (`MEMORY.md`).

This is how Carina becomes more knowledgeable about its operators and users over time without
manual input.

## RAG (Retrieval-Augmented Generation)

### Schema

The `rag_chunks` table in PostgreSQL (requires pgvector extension):

```sql
rag_chunks (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  source      text NOT NULL,    -- file path or URL that was chunked
  pack        text NOT NULL,    -- skill pack name or 'custom' for uploaded docs
  content     text NOT NULL,    -- the chunk text (up to ~2000 chars)
  embedding   vector,           -- pgvector embedding
  metadata    jsonb DEFAULT '{}'-- optional: title, author, tags, url
)
```

Index: `rag_chunks` has a pgvector index enabling efficient cosine similarity search with the
`<=>` operator.

### Embedding Providers

Embeddings are generated by one of three providers, selected automatically based on available
API keys:

| Provider | Model | Dimensions | Priority |
|---|---|---|---|
| Gemini | `text-embedding-004` | Configurable | High |
| Voyage AI | `voyage-3` | Configurable | Medium |
| OpenAI | `text-embedding-3-small` | 1536 | Fallback |

Provider selection chain: check `CARINA_EMBEDDING_PROVIDER` env override first, then try
each configured provider in priority order. `embeddingProviderStatus()` reports which provider
is active.

### Ingestion Pipeline

The CLI command `carina ingest --pack <packname>` runs `src/skills/ingestion.ts`:

1. Walk all `.md` files in the pack's `knowledge/` directory
2. Check `isSourceIngested(filePath)` - skip files already in `rag_chunks` (idempotent)
3. Split content at heading boundaries (`## ` and `### `) targeting 2,000-char chunks
4. For each chunk: call `embed(content)` to generate embedding vector
5. Call `insertRagChunk(source, pack, content, embedding, metadata)` to persist

Additionally, the ingestion pipeline processes files from `archive/property-saas-spec/` (the
property domain archive directories: `docs/` and `architecture/`).

### RAG Query

During agent turns, the orchestrator calls `searchRag(query, limit)`:

```typescript
// Returns up to `limit` chunks closest to the query embedding
const hits = await searchRag(userQuery, 5);
// Each hit: { id, source, pack, content }
// Injected into system context as domain knowledge
```

The SQL behind this is a pgvector cosine distance query:
```sql
SELECT id, source, pack, content
FROM rag_chunks
WHERE embedding IS NOT NULL
ORDER BY embedding <=> $1   -- $1 is the query embedding vector
LIMIT $2
```

### Platform Knowledge Injection

In addition to RAG, two static files are loaded at server startup and injected into every agent
turn:

- `src/platform/platform-knowledge.md`: Monorepo structure, product boundaries, active projects
- `src/platform/platform-state.md`: Current operational state (updated manually or by automation)

These files are read once at startup (`preloadPlatformKnowledge()`) and cached in memory.
`buildPlatformKnowledgeContext()` formats them for injection into the agent system prompt.

### Session Search

The `session-search` tool (`src/tools/session-search.ts`) is a full-text search tool that
searches across all past session messages, not just the pgvector RAG. It uses SQLite FTS5 (when
the builtin backend is active) or PostgreSQL full-text search for the postgres backend.

This allows the agent to recall "what did the user say last week about X?" from raw conversation
history rather than from distilled memory.

## Memory Discipline

`src/memory/memory-discipline.ts` enforces context budget rules:
- Maximum tokens allocated to memory injection per turn
- Priority ordering: platform knowledge > RAG hits > persistent memory > session history
- Truncation strategy when budget is exceeded: truncate oldest session history first

`src/memory/context-budget.ts` manages the token accounting across all injected context.

## RAG CLI Commands

```bash
carina rag status           # Show active embedding provider, dimensions, configuration
carina rag search <query>   # Search rag_chunks and display top 10 results
carina rag ingest           # Run ingestion for default pack (property-uk)
carina ingest --pack <name> # Run ingestion for a specific pack
```

## Aiva Knowledge Base (Per-Worker)

Separate from the global RAG system, each Aiva worker has its own knowledge base
(`src/workers/knowledge-base.ts`). This stores:

- `document` type: free-text knowledge documents (max 20,000 chars each)
- `faq` type: question-answer pairs (max 500 chars each)

The total knowledge base per worker is capped at 50,000 characters (configurable for Business
plan). Knowledge entries are injected into the Aiva worker's persona prompt at the start of
each session, making the worker context-aware about the specific business it serves.

This is separate from the global RAG because Aiva workers are multi-tenant: different clients
have different knowledge that must not leak between workers.
